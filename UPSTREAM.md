## CodeIgniter 4 — `user_guide_src/source/installation/running.rst`

**Where:** `codeigniter4/CodeIgniter4`, the "Running Your App" page, after the
"Worker Mode with FrankenPHP" section (which today is the only
application-server alternative to Apache/nginx the guide names).

**Why:** CI4 runs unmodified on ePHPm in per-request mode (recipe
`apps/codeigniter4`, tested on 4.7.5). ePHPm replaces the web server + PHP-FPM
pair with one binary; worker mode is deliberately *not* claimed, since CI4's
worker entrypoint is FrankenPHP-specific.

**Proposed text (reStructuredText):**

```rst
*******************
Hosting with ePHPm
*******************

`ePHPm <https://github.com/ephpm/ephpm>`_ is a single-binary PHP application
server that embeds the PHP runtime, so a CodeIgniter app needs neither a web
server nor PHP-FPM in front of it. Point its document root at **public/** and
give it the same rewrite rule as **public/.htaccess**:

.. code-block:: toml

    # ephpm.toml
    [server]
    listen = "0.0.0.0:8080"
    document_root = "/var/www/myapp/public"
    fallback = ["$uri", "$uri/", "/index.php?$query_string"]

.. code-block:: console

    ephpm serve --config ephpm.toml

``spark`` runs on the embedded interpreter with ``ephpm php spark migrate``.
A ready-to-run Docker recipe (with MariaDB, and a single-container variant on
ePHPm's embedded database) is maintained at
`github.com/ephpm/recipes <https://github.com/ephpm/recipes/tree/main/apps/codeigniter4>`_.

.. note:: ePHPm has its own persistent worker mode, but the worker entry
    point generated by ``php spark worker:install`` is specific to FrankenPHP
    and does not run on it; use ePHPm's default per-request mode.
```

## SolidInvoice — `src/InstallBundle/Command/InstallCommand.php`

**Where:** `SolidInvoice/SolidInvoice` 3.0.1, `InstallCommand::install()`
(the `bin/console app:install` command). This is a bug-fix proposal rather
than a docs addition; not an ePHPm issue — it reproduces with any PHP.

**Why:** `install()` loops over the `InstallationStepInterface` services and
calls `$step->execute(new Installation(), $callback)`, but every step's
`execute()` is a generator (`CreateDatabaseStep`, `RunMigrationsStep`,
`GenerateBuildIdStep`, … all `yield from $callback(...)`) and the returned
`Generator` is discarded without being iterated, so no step body runs. The
web installer (`InstallBundle\Action\Install`) consumes the same steps
correctly through `yield from $step->execute(...)`. On the CLI,
`Running step: Creating database schema` prints and nothing happens, then
`Creating Admin User` fails with `SQLSTATE[42S02]: Base table or view not
found: 1146 Table 'solidinvoice.users' doesn't exist`. (The secret and the
database settings are still written, by `saveConfig()`, which is why a
second run after building the schema by hand succeeds.) Note that the
callback is `void`, so `yield from $callback(...)` would throw once the
generator is iterated; the callback has to return an iterable too.

**Proposed change (PHP):**

```php
foreach ($this->installationSteps as $step) {
    $output->writeln(sprintf('<info>Running step: %s</info>', $step->getLabel()));
    $messages = $step->execute(new Installation(), static fn (string $content): iterable => [$content]);
    foreach ($messages as $content) {
        $output->writeln($content, OutputInterface::VERBOSITY_VERBOSE);
    }
}
```

Until then the recipe (`apps/solidinvoice/entrypoint.sh`) reproduces what the
web installer does: `app:install --skip-user` (seeds the vault; fails at the
end), `doctrine:schema:update --force --complete` +
`doctrine:migrations:version --add --all`, then `app:install` again (admin
user, installed marker).
